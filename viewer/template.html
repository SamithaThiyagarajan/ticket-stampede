Ticket Stampede

A ticket-selling service designed to sell exactly 100 tickets, safely, when tens of thousands of purchase requests arrive within about a minute — and to stay correct when its database fails.

Every number on this page comes from saved experiment results. Read it top to bottom; each section answers one question.

What problem are we solving?

A flash sale: far more people want a ticket than there are tickets, and they all click at almost the same moment. The service must sell each of the 100 tickets exactly once, answer everyone else clearly, and never contradict itself.

How it is built

Requests flow top to bottom. The sellers keep no ticket state of their own; every decision is made in PostgreSQL, the single source of truth. That is what lets three sellers run side by side without coordinating.

Scale of the assignment workload

The brief describes up to 50,000 people arriving within the same 60 seconds. That is an arrival rate of about 833 per second — not 50,000 simultaneous connections, which is not what we model.

What does “correct” mean?

“It didn't crash” is not enough. Every run is checked against five rules, recomputed independently from the raw request log and the final database state — not taken from the service's own claims.

  1. No overselling — never more than 100 tickets are issued.
  2. No duplicate ticket numbers — two purchases can never receive the same ticket.
  3. Idempotency — retrying the same request_id returns the same ticket instead of creating another one.
  4. Response consistency — every “you got ticket N” answer agrees with the final database state, and nobody told “sold out” holds a ticket.
  5. Counter consistency — the stored sold_count equals the number of actual ticket rows.

Why does the naive version fail — and how does the final one fix it?

The obvious implementation works perfectly when requests arrive one at a time — and breaks badly when they arrive together.

Naive version (built first, on purpose)

READ sold_count (e.g. 41) ↓ check capacity (41 < 100, OK) ↓ INSERT ticket 42 ↓ UPDATE sold_count = 42 ⚠ race condition

Many buyers can read the same available state (“41 sold”) before any of them writes, so several of them all issue ticket 42, and the counter update is lost.

Final version: one transaction with a row lock

BEGIN lock the sale row (SELECT … FOR UPDATE) has this request_id bought already? → return it any tickets left? → else 409 issue ticket sold_count + 1 update sold_count COMMIT (lock released)

SELECT … FOR UPDATE locks the one row that holds the inventory. Only one transaction at a time can make the decision about the remaining inventory; the others wait their turn and then see the updated count. Database constraints (primary key on the ticket number, unique request_id, a check that sold_count never exceeds the total) are a second line of defence.

What if the same purchase is sent twice?

Networks fail and people double-click, so the same purchase request can arrive more than once. Every request carries a request_id chosen by the buyer; the service promises that one request_id produces at most one ticket.

The rule

request_id = A → ticket 57 retry request_id = A → ticket 57 again (no new ticket) request_id = B → another ticket
  • One purchase request (one request_id) produces at most one ticket, however many times it is sent.
  • A different request_id is a different purchase, even from the same user: this assignment has no one-ticket-per-user rule (the schema has no per-user constraint; not load-tested separately).
  • Re-using a request_id with a different user is rejected (HTTP 422), so a reused id cannot hand one buyer's ticket to another (checked by hand during development; not part of the saved load tests).

Evidence: every request sent 10 times, across three sellersM9 F2

Each request_id was sent as 10 simultaneous copies, spread by the load balancer over all three sellers — the hardest version of “retry while the original is still in flight”.

What happened under 50,000 arrivals?

The load generator is open-loop: it sends requests on a fixed schedule — about 833 per second — whether or not earlier requests have finished, like real independent buyers. A run only counts if the load generator itself kept to its schedule; otherwise we would be measuring the client, not the service.

How to read the numbers: throughput = responses completed per second · p50 = median latency (half the requests were faster) · p99 = the latency of the slowest 1% of requests. In the reference run, most of the p99 came from requests arriving in the first seconds, while the 100 tickets were being sold through the lock (visible in the optional replay at the bottom of the page).

What happened when PostgreSQL failed?

All sellers depend on the one database. These experiments deliberately broke it during the assignment workload and then checked that nothing was oversold, duplicated or lost. They test specific failures — not every possible one.

Three different things happen in each experiment and should not be confused: (1) expected database errors — sellers answer HTTP 500 while PostgreSQL is gone; (2) nginx 502 “no live upstreams” — the load balancer takes sellers out of rotation after connection errors and keeps them out for a while; (3) correctness after recovery — the five checks plus a replay of every uncertain request.

What if a purchase commits but the response is lost?

The subtlest failure: PostgreSQL commits the purchase successfully, but the confirmation never reaches the buyer. The buyer sees an error — yet they own a ticket. A random crash almost never lands in this sub-millisecond window, so we created it deliberately.

The scenario

How it was createdM12

A small test-only proxy sat between one seller and PostgreSQL. It understood the database protocol and, for some transactions, dropped PostgreSQL's “COMMIT complete” reply after the commit had already happened. The application code was not changed.

Result

For every committed-but-unacknowledged purchase: the buyer's only answer was a failure, PostgreSQL holds the ticket, and replaying the same request_id returned that exact ticket — without creating another. This is the case idempotency exists for: without a request_id, the buyer's only safe move would be to buy again, and they would end up with two tickets.

Where did the system saturate?

The 833/s benchmark shows the required load is handled; it does not show how much headroom there is. So the offered rate was raised step by step (60 s each), with validity rules fixed before running.

What the sweep shows — and what it does not

    Why seller CPU: where a seller process spends its time (CPU profile under load)

    A sampling profile of one seller under load showed its time going to HTTP parsing, the web framework and the event loop — not to database work. It is from a separate diagnostic run whose throughput is not a benchmark.

    What happens after the tickets sell out?

    Once all 100 tickets are gone, nearly every later request only needs to learn “sold out”. Making each of them queue for the inventory lock would waste the lock on a question whose answer cannot change — tickets are never returned during a sale in this design.

    The sold-out fast path

    one database read (one snapshot): does this request_id already own a ticket? → return that ticket otherwise, is the sale sold out? → 409 sold out otherwise → the locked purchase path

    An old request_id must still be checked first, because it may be a retry of a purchase that committed. Both facts are read in one database snapshot: since a ticket and its counter update commit together, a snapshot that says “sold out” also contains every ticket row, so “sold out and not yours” is final. Reading them separately would reopen a race.

    Evidence: with vs without the fast path, 300 arrivals/sM7 A/B

    Same workload and code, only the fast path switched on or off; three runs each, alternating.

    Which decisions did we make?

    Each choice below was made for a reason we can defend, and each is separated into what this submission implements and what a production system would add.

    DecisionWhat we implementedIn production
    PostgreSQL is the source of truthAll ticket state lives in PostgreSQL; sellers are stateless and can be added or restarted freely.Same principle, with the database made highly available (see Production extensions).
    A row lock protects the inventory decisionSELECT … FOR UPDATE on the single sale row serializes the check-then-issue step.Same; shorten the time the lock is held (e.g. one database round trip per purchase) if inventory were large.
    Constraints as defence in depthPrimary key on ticket number, unique request_id, sold_count checked against the total. Shown working: the naive code on the constrained schema issued no extra tickets (but failed many requests).Same.
    No application-level lockRejected: an in-process lock (e.g. Python asyncio) protects one process only; it does nothing across three sellers or several worker processes.Same.
    Row lock rather than SERIALIZABLEThe row lock expresses the critical section directly. SERIALIZABLE would be expected to make concurrent buyers of the same row fail with serialization errors and retry under a stampede (reasoning; not benchmarked).Same, unless a workload needed serializable guarantees across many rows.
    No RedisNot needed: the observed limiting component was seller CPU, not the database, and a second store would create a second source of truth to keep consistent.Only if a measured bottleneck required it.
    No KubernetesDocker Compose runs the whole topology reproducibly on one machine.An orchestrator for multi-host deployment and restarts.
    No PostgreSQL replication/failoverDeliberately not implemented. Asynchronous failover could lose an acknowledged sale and sell its ticket number again; a safe failover needs synchronous replication, fencing and more — a large system on its own, and on one physical host it would remove no real failure.Synchronous replication with a standby quorum, fenced leader election, routing to the current primary.

    What are the limitations?

    These are specific, not disclaimers: each says exactly where the evidence stops.

      What would production add? (not implemented)

      What a production deployment would add. None of this is part of the submission.

      • Highly available PostgreSQL: synchronous replication to a quorum of standbys, fenced leader election, and clients routed only to the current primary.
      • Active seller readiness checks in the load balancer, and returning “503 try again” for database errors instead of an unhandled 500.
      • Controlled retries of connection-level failures — safe only because of request_id idempotency, and limited to one retry to avoid retry storms.
      • Multi-host deployment, so a single machine is no longer a single failure domain.
      • Production observability: metrics, alerting and tracing beyond these offline experiment reports.
